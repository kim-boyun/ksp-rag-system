# RAG 시스템 고도화 방안 총정리

이 문서는 **Anthropic Contextual Retrieval**([참고](https://www.anthropic.com/engineering/contextual-retrieval))과 일반적인 RAG 고도화 기법을 종합한 전체 로드맵입니다.

---

## 1. 개요: 개선이 일어나는 구간

```
[질의] → [쿼리 전처리] → [검색] → [리랭킹] → [프롬프트 구성] → [답변 생성] → [후처리]
              ↑                ↑         ↑              ↑              ↑
           고도화 포인트    인덱스 품질   고도화 포인트   프롬프트/컨텍스트  (선택)
```

- **인덱스/검색**: 인제스트·인덱스 빌드 시 맥락 추가(Contextual Retrieval), 청킹·임베딩 개선
- **쿼리 전처리**: 질문 재작성, 쿼리 확장, HyDE
- **리랭킹**: LLM 리랭킹, 크로스 인코더 리랭킹
- **생성**: 프롬프트 정교화, 컨텍스트 전달 방식

---

## 2. 인덱스·검색 품질 (Contextual Retrieval + 기타)

### 2.1 Contextual Retrieval (Anthropic 권장)

**목적**: 청크만으로는 맥락이 부족해 검색이 실패하는 경우를 줄임.

| 기법 | 설명 | 적용 위치 |
|------|------|-----------|
| **Contextual Embeddings** | 각 청크 앞에 "문서 내 맥락 설명(50~100토큰)"을 LLM으로 생성해 붙인 뒤 **임베딩** | 인덱스 빌드 시 (인제스트 또는 index-elastic) |
| **Contextual BM25** | 같은 "맥락 + 청크" 문자열로 **BM25 인덱스**도 생성 | 동일 |

**프롬프트 예시** (Anthropic 스타일):

```
<document> {{문서 전체 또는 해당 섹션}} </document>
<chunk> {{청크 원문}} </chunk>
이 청크를 문서 전체 맥락 안에서 설명하는 짧은 문맥(50~100토큰)만 작성하세요. 검색 품질 향상을 위한 문맥입니다. 문맥만 출력하세요.
```

**저장 구조 제안**:
- `content`: 원문 청크 (답변 생성 시 사용)
- `contextualized_content`: 맥락 + 원문 (검색·임베딩·BM25용)
- 검색은 `contextualized_content`로 수행, 반환 시 `content`를 프롬프트에 넣거나, 맥락+원문을 함께 넣고 "맥락과 본문 구분" 지시 추가

**참고**: [Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) 실험 기준 검색 실패율 약 35%↓(임베딩), 49%↓(임베딩+BM25), 리랭킹 포함 시 67%↓.

### 2.2 청킹 전략

| 항목 | 설명 | 설정/코드 |
|------|------|-----------|
| 크기·오버랩 | 너무 작으면 맥락 손실, 크면 노이즈 증가 | `CHUNK_SIZE`, `CHUNK_OVERLAP` (.env) |
| 경계 | 문단/섹션 단위로 자르면 품질 향상 | `chunkers.py` 등에서 스플리터 옵션 |
| 표/그림 | 지금처럼 별도 청크 유지 권장 | 유지 |

| 항목 | 설명 |
|------|------|

## 3. 쿼리 전처리 (검색 전 단계)

| 기법 | 설명 | 난이도 | 비고 |
|------|------|--------|------|
| **쿼리 확장** | 질문을 여러 표현으로 바꿔 각각 검색 후 RRF 병합 | 쉬움 | 이미 있음. `QUERY_EXPANSION_ENABLED`, `QUERY_EXPANSION_NUM_QUERIES` |
| **질문 재작성** | 사용자 질문을 **검색에 유리한 한 문장**으로 한 번만 재작성 후 검색 | 보통 | Retriever 직전 LLM 1회 호출 |
| **HyDE** | 질문에 대한 **가상 답변**을 LLM으로 생성 → 그 문단을 **임베딩**해서 검색 | 보통 | 질문 문자열만으로 검색할 때보다 문서와 의미 유사도 향상 |

---

## 4. 리랭킹

| 기법 | 설명 | 난이도 | 비고 |
|------|------|--------|------|
| **LLM 리랭킹** | 검색 결과를 LLM으로 관련도 점수(0–100) 매겨 재정렬 | 쉬움 | 이미 있음. UI/CLI "LLM 리랭킹 사용" 또는 `--rerank` |
| **크로스 인코더 리랭킹** | (query, document) 쌍을 한 번에 넣어 관련도 점수 산출. 보통 LLM보다 빠르고 안정적 | 보통 | `rerankers/`에 CrossEncoder 기반 모듈 추가 가능 |

**참고**: Contextual Retrieval 글에서는 초기 검색 top-150 → 리랭크 후 top-20 전달 시 실패율 67% 감소. 본 시스템에서는 `TOP_K`로 초기 검색량, `RERANK_TOP_K`로 최종 전달량 조정.

---

## 5. 검색량·설정 튜닝 (즉시 적용 가능)

| 설정 | 설명 | 권장 |
|------|------|------|
| `TOP_K` | 1차 검색으로 가져올 문서 수 | 12 → 15~20 (리랭킹 사용 시) |
| `RERANK_TOP_K` | 리랭킹 후 답변에 넣을 문서 수 | 5~10 (문서 길이·모델 컨텍스트에 맞게) |
| `LLM_MAX_TOKENS` | 답변이 잘리면 | 2048 등으로 상향 |
| `QUERY_EXPANSION_NUM_QUERIES` | 쿼리 확장 개수 | 3~5 |

---

## 6. 프롬프트·생성 단계

| 항목 | 설명 |
|------|------|
| **qa.txt 정교화** | "출처만 참고", "모르면 모른다고", "사고 과정 출력 금지" 등 규칙 명확화 → 환각·형식 개선 |
| **컨텍스트 전달** | Contextual Retrieval 적용 시, 답변에는 원문(`content`)만 넣거나, 맥락+원문을 넣고 "맥락과 본문을 구분해 참고하라" 한 줄 추가 (Anthropic 권장) |

## 7. 적용 우선순위 제안

| 순서 | 구간 | 방안 | 난이도 | 비고 |
|------|------|------|--------|------|
| 1 | 설정 | LLM 리랭킹 켜기, TOP_K/RERANK_TOP_K/쿼리 확장 개수 튜닝 | 쉬움 | 즉시 |
| 2 | 인덱스 | **Contextual Retrieval** (맥락 생성 후 임베딩·BM25에 사용) | 보통 | 인덱스 재구축, LLM은 기존 유지 가능 |
| 3 | 쿼리 | 질문 재작성 또는 HyDE 도입 | 보통 | Retriever 직전 단계 |
| 4 | 리랭킹 | 크로스 인코더 리랭커 추가 (선택) | 보통 | LLM 리랭킹 대체 또는 1차 후보 축소용 |
| 5 | 청킹·임베딩 | 청크 경계·크기 실험, 임베딩 모델 업그레이드 | 보통 | 인덱스 재구축 |
| 6 | 생성 | 프롬프트·컨텍스트 전달 방식 정리 | 쉬움 | qa.txt, 컨텍스트 필드 선택 |
